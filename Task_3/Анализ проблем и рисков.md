# Задание 3. Переход на Event-Driven архитектуру
## Контекст
Сервисы core-app и ins-comp-settlement получают данные о доступных продуктах через REST API сервиса ins-product-aggregator. 

В момент вызова он:
* запрашивает информацию из всех страховых компаний (сейчас их пять),
* агрегирует её в единый список,
* возвращает этот список в рамках того же синхронного запроса.

Чтобы ускорить работу сервисов, при изначальном проектировании команда решила хранить локальные реплики данных о продуктах и тарифах в сервисах core-app и ins-comp-settlement.

Сервис core-app осуществляет запрос к ins-product-aggregator раз в 15 минут, а ins-comp-settlement - раз в сутки (ночью), при формировании реестра оформленных страховок. 

Иногда команда сталкивается с ошибками взаимодействия между этими сервисами. Они связаны с задержками ответов или ошибками при взаимодействии с API страховых компаний.

Дополнительно сервис ins-comp-settlement раз в сутки осуществляет запрос в core-app по REST API для получения всех оформленных за день страховок. 

В ближайшее время InsureTech планирует подписать агентское соглашение ещё с пятью страховыми компаниями.

## Анализ рисков компании в связи с ростом числа партнерских компаний до 10+

#### Проблема 1. Синхронный вызов API страховых компаний в одном запросе
| №  | Риски                                                                                                                                                                            |
|:---|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| R1 | Время ответа сервиса ins-product-aggregator растет линейно с ростом числа партнерских API.<br/>Возможно превышение таймаутов вызывающих сервисов.                                |
| R2 | Сервис ins-product-aggregator должен параллельно опрашивать 10+ компаний, что требует сложной логики таймаутов, повторных попыток и обработки ошибок.                            |
| R3 | Каскадные сбои: при задержках или ошибках в API одной страховой - вызывающий сервис может не получить ответ и по всем остальным 9+ компаниям, которые могли бы ответить успешно. |

#### Проблема 2. Возможна неконсистентность данных
| №  | Риски                                                                                                                                                                                          |
|:---|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| R1 | Информация о продуктах может быть утеряна, если в core-app или ins-comp-settlement данные не зафиксировались в БД из-за сбоя.                                                                  |
| R2 | Информация по продуктам в сервисах core-app и ins-comp-settlement обновляется с разной периодичностью. Следствием может быть неконсистентность данных и, следовательно, неточности в расчетах. |
| R3 | В контуре агрегатора нет единого "источника правды" о страховых продуктах, что затруднит расследование инцидентов и тикетов саппортов.                                                         |

#### Проблема 3. Синхронная связность сервисов
| №  | Риски                                                                                                                                                                                                                                                                 |
|:---|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| R1 | Cервис ins-comp-settlement обращается к core-app по REST API за всеми оформленными страховакми. Есть риск создания пиковой нагрузки на core-app и БД в момент вызова.                                                                                                 |
| R2 | Синхронная связь создает проблему "медленного потребителя", сервисы жестко связаны по времени ответа. Это нарушает принцип слабой связанности и мешает масштабировать сервисы независимо друг от друга - узким местом становится самый медленный компонент в цепочке. |

#### Проблема 4. Сложности трассировки, отладки, аудита
| №  | Риски                                                                                                                                                                                                          |
|:---|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| R1 | Синхронная цепочка вызовов (core-app -> aggregator -> 10+ компаний) создает сложности с трассировкой и отладкой: при возникновении ошибки сложно определить, какая именно страховая компания вызвала проблему. |
| R2 | При отсутствии централизованного хранения данных о продуктах (каждый сервис хранит свою копию) возникают сложности с аудитом: какие тарифы были актуальны на определенный момент времени.                      |
